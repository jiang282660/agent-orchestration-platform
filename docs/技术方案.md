# 大模型 Agent 工具编排调度平台 —— 架构设计与技术方案

> 赛题：大模型 Agent 工具编排调度平台（多智能体协作的编排、调度、执行与验证）
> 技术栈：Python + FastAPI · DeepSeek API · 自研编排内核 · Vue3 前端
> 业务场景：**基于知识库的多智能体研究报告生成平台**

---

## 1. 项目概述

### 1.1 背景与对标

本平台对标 **LobeHub**、**DeepSeek Harness** 等主流 Agent Harness 框架，重点解决多智能体协作中的
**编排（Orchestration）、调度（Scheduling）、执行（Execution）、验证（Verification）** 四大问题，
形成"知识库 → 团队 → 工作流 → 动态调度 → 自我循环 → 验证反馈"的完整工程闭环。

与直接套 LangChain/LangGraph 不同，本方案**自研编排内核**，仅复用 LLM SDK 与向量检索组件，
使评分点（Agent 工具循环、编排、动态调度、Self-Loop、验证反馈）全部自主可控、可解释、可演示。

### 1.2 目标

| 能力点 | 目标 |
|---|---|
| 知识库定义与集成 | 多知识库、多文档格式入库、可插拔检索（语义+关键词混合） |
| Agent 团队定义 | 声明式定义 Agent（角色/提示词/工具/参数），每个 Agent 具备 **ReAct 多步工具循环**能力 |
| 工作流编排 | 通用 DSL 定义 DAG（顺序/并行/条件分支/子工作流） |
| 动态调度 | 运行时按规划结果动态展开/插入节点，并行调度，带并发控制 |
| Self-Loop | "执行→评估→反馈→重执行"声明式循环，阈值 + 轮次上限 |
| 结果验证与反馈 | 评分 + 规则核查 + **小基准集（golden set）**，量化优化前后提升 |

## 2. 业务场景：研究报告自动生成

**场景闭环**：用户上传资料文档建立知识库 → 提交"撰写《某主题》研究报告"任务 →
平台组建 Agent 团队 → 编排引擎逐步执行（规划 → 检索 → 分析 → 撰写 → 审校 → 循环优化）→
输出一份**带引用溯源、经过多维验证评分**的最终报告。

### 2.1 角色团队（Agent Team）

| Agent | 职责 | 关键工具 |
|---|---|---|
| planner 规划者 | 拆解主题为子任务大纲，决定检索策略 | 大纲生成、子任务分解 |
| retriever 检索者 | 多轮检索知识库片段并附来源 | kb_search（混合检索） |
| analyzer 分析者 | 对检索材料归纳、提炼论点与证据 | 引用整理、去重 |
| writer 撰写者 | 按大纲生成报告正文并标注引用 | 章节撰写、引用标注 |
| reviewer 审校者 | 结构化评分 + 具体修改反馈 | 评分 schema |
| verifier 验证者 | 事实核查：断言是否被引用支撑、矛盾检测 | 引用溯源 |

### 2.2 如何覆盖六大能力点

- **知识库**：文档上传解析 → 分块 → 向量化 → 混合检索。
- **团队**：六角色声明式定义，各自具备 ReAct 工具循环。
- **编排**：`planner → [retriever → analyzer] → writer → reviewer` 的 DAG。
- **动态调度**：planner 运行时产出 N 个子任务，调度器把每个子任务展开为
  `retriever→analyzer` 子图并行执行，再汇聚给 writer。
- **Self-Loop**：`writer → reviewer` 构成质量循环，评分低于阈值则携带反馈重写。
- **验证反馈**：reviewer 评分（门禁）+ verifier 引用溯源（事实核查）+ 小基准集（客观量化）。

## 4. 核心模块详细设计

### 4.1 知识库模块（Knowledge Base）

- **定义**：`name`、`description`、`embedding_model`、`chunk_size`、`chunk_overlap`、`retriever 类型`。
- **文档解析**：PDF（pypdf）、Markdown/TXT（原生）、Word（python-docx，可选）。
- **分块**：语义优先（标题/段落边界）+ 固定长度兜底，保留 chunk 元数据（来源、页码、序号）。
- **向量化与检索**：可插拔 `Retriever` 抽象，默认混合检索：
  - 语义：本地 embedding（`BAAI/bge-m3` 或 `bge-small-zh`）+ ChromaDB；
  - 关键词：jieba + BM25；
  - 融合：RRF 合并，返回 Top-K 片段与来源。
- **降级**：无向量模型时退化为纯 BM25，保证链路可跑通。

> DeepSeek API 无 embedding 端点，故 embedding 用本地模型（免费、离线、可控），
> 通过接口抽象可切换第三方。

### 4.2 Agent 运行时（ReAct 多步工具循环）

**Agent 定义**：

```
Agent {
  id, name, role_prompt,        # 角色与系统提示词
  tools: [Tool],                # 可用工具
  llm_config,                   # 模型、温度、max_tokens
  input_schema, output_schema,  # 输入输出契约（结构化校验）
  max_steps,                    # ReAct 最大步数上限
}
```

**ReAct 执行循环**（每个 Agent 节点的运行方式）：

```
while step < max_steps:
    resp = llm.chat(messages, tools=agent.tools, response_format=...)
    if resp 有 tool_calls:              # 模型决定调用工具
        逐个执行工具 → 结果以 tool 消息回填 messages
    else:                                # 模型决定结束
        output = 结构化解析(resp.content)  # Pydantic 校验
        return output                     # 解析失败则带错误重试（≤2 次）
```

- **工具（Tool）**：统一 JSON Schema 描述，分本地工具（`kb_search` 等直接调 Python 函数）
  与 LLM 工具（走 DeepSeek function-calling）。
- **混合节点边界**：retriever 的 `kb_search` 是确定性检索函数；retriever Agent 通过
  ReAct 循环"生成检索意图 → 调 kb_search → 据结果补充检索 → 综合带引用结论"，
  这是真·工具循环能力的落点。
- **结构化输出可靠性**：`response_format={"type":"json_object"}` + Pydantic schema 校验，
  失败重试 ≤2 次并附解析错误反馈，仍失败则用兜底默认值并标记 `degraded`。

### 4.3 工作流编排引擎 + RunState 状态

**节点间数据传递：共享 `RunState` 状态对象**（类似 LangGraph State）。

- 每个节点声明 `reads: [keys]`（从 state 读哪些字段）与 `writes: [keys]`（写哪些字段）；
- 调度器执行节点时传入 `RunState` 的只读视图，节点返回局部更新，调度器合并回 state；
- 全程 state 变化落库到 `run_steps`，可回溯、可复现、可画执行轨迹。

**工作流 DSL**（YAML/JSON）：

```yaml
name: research_report
nodes:
  - id: planner
    agent: planner_agent
    reads: [topic]
    writes: [outline, subtasks]
  - id: retriever
    agent: retrieval_agent
    depends_on: [planner]
    writes: [evidence]
  - id: analyzer
    agent: analysis_agent
    depends_on: [retriever]
    writes: [analysis]
  - id: writer
    agent: writer_agent
    depends_on: [planner, analyzer]
    writes: [draft]
  - id: reviewer
    agent: review_agent
    depends_on: [writer]
    writes: [score, feedback]
loops:                          # Self-Loop 声明
  - name: quality_loop
    body: [writer, reviewer]    # 循环体（子工作流）
    condition: "review.score < 0.8 and loop.iteration < 3"
    feedback: "reviewer.feedback -> writer.context"
verifier:
  agent: verifier_agent
  trigger: after_all            # 出循环后的最终事实核查
```

**引擎职责**：解析 DSL 为 DAG（环检测 + 拓扑校验）；按"所有依赖完成即就绪"触发节点；
节点级重试、超时、异常兜底。

### 4.4 动态调度器（Scheduler）

- 基础：基于 DAG 拓扑的就绪队列 + asyncio 并行执行。
- **动态调度（运行时图展开）**：planner 输出 `subtasks` 列表 → 调度器把每个子任务实例化为
  `retriever→analyzer` 子图，并行调度，结果汇聚回 state。
- 并发上限 + 优先级，避免爆 token / 触发 DeepSeek 限流。

### 4.5 Self-Loop 循环控制器

- 把"执行→评估→反馈→重执行"抽象为声明式循环（DSL `loops`）；
- 三要素：**循环条件**（评分阈值/轮次上限）、**反馈通道**（评估结果注入上游 context）、
  **状态传递**（每轮携带历史反馈）；
- 记录每轮评分曲线，供演示与基准对比。

### 4.6 结果验证与反馈（Verifier + 基准集）

**三层验证**：

1. **规则核查**：引用存在性、章节完整性、篇幅、格式合规（确定性，客观）。
2. **LLM 评分**：reviewer 结构化输出四维评分（相关性/准确性/完整性/流畅性）+ 具体反馈。
   - reviewer 进循环当质量门禁；verifier 出循环做最终事实核查。
3. **小基准集（golden set）**：固定文档集 + 3~5 个固定问题 + 人工标注的"必覆盖要点"清单，
   用规则/LLM 检查要点覆盖度，**量化展示"反馈优化前后"的得分提升**（客观、有说服力）。

## 5. 技术选型

| 层 | 选型 | 理由 |
|---|---|---|
| Web 框架 | FastAPI + Uvicorn | 异步、自动 OpenAPI、SSE 流式 |
| LLM | DeepSeek API（`openai` SDK 兼容协议） | 赛题对标、国内可用、成本低 |
| 编排内核 | **自研**（不依赖 LangGraph） | 评分点全链路自主可控、可解释 |
| Agent 循环 | 自研 ReAct（基于 DeepSeek function-calling） | 真·工具循环能力，可控 |
| Embedding | sentence-transformers（bge-m3/bge-small-zh） | 本地免费、离线、中文好 |
| 向量库 | ChromaDB（持久化） | 轻量、元数据过滤 |
| 关键词检索 | jieba + rank_bm25 | 无模型降级兜底 |
| 元数据存储 | SQLite（SQLAlchemy） | 零配置、单文件 |
| 前端 | **Vue3 + Element Plus + Vite** | 完整演示页面（知识库/看板/报告/评分） |
| 前端通信 | fetch + SSE（EventSource） | 执行流式推送、评分曲线 |

> 运行时：本机 Python 3.14.7，部分 ML 库对 3.14 适配可能滞后，
> 建议 `python -m venv` 建 **3.11/3.12** 虚拟环境降低兼容风险。

## 8. 关键流程时序

```
用户 ─► API(/runs) ─► Scheduler
                        │ 1. planner（ReAct）：拆解子任务大纲 → state.outline/subtasks
                        │ 2. 图展开：每个子任务生成 retriever→analyzer 子图
                        │ 3. 并行调度 retriever(ReAct: kb_search 多轮检索) → analyzer
                        │ 4. 汇聚 → writer 生成初稿
                        │ 5. reviewer 评分 → Loop Controller 判断
                        │      ├─ 不达标：feedback 注入 writer，回到 4（≤3 轮）
                        │      └─ 达标：verifier 引用溯源/事实核查
                        │ 6. 输出终稿 + 评分曲线 + 引用列表（可跑基准集量化）
用户 ◄─ SSE 事件流（节点开始/结束/工具调用/评分） ◄─ 执行中实时推送
```

### 12.4 与设计的差异说明（如实）

- 语义检索**已启用**：`HybridRetriever` 用「BM25 关键词 + 语义向量」做 RRF 混合；embedding 后端可插拔
  （优先 sentence-transformers，本机实际走轻量 `fastembed`/ONNX 的 `bge-small-zh-v1.5`，免 torch）。
  向量暂存内存（`Retriever` 抽象预留 ChromaDB 切换点），未装 embedding 依赖时自动降级纯 BM25，链路可离线跑通。
- `runs` / `run_steps` **已落 SQLite**（`RunRow` / `RunStepRow`），运行生命周期与每节点轨迹（含 tokens/latency/降级标记）可回溯；
  `evaluations` 仍并入工作流返回，未单独拆表。
- `teams` 表未单独建模，团队以「预置六角色 Agent」方式组织。
- API 中 `GET /api/runs/{id}/report`、`POST /api/runs/{id}/evaluate` 合并进工作流（verifier 节点 + 运行结果返回），未拆独立端点。
